# Michelson interferometer simulator

A single-page, dependency-free simulator. You edit a source spectrum. The page then shows the Michelson interference pattern, the interferogram, the interfered spectrum and the coherence length. The page ships as one file, `index.html` (HTML, CSS and JS), which is what gets published as the artifact. MathJax 3.2.2 is loaded from the jsDelivr CDN.

## How we work (Kiva's preferences)

- **Roadmap:** `ROADMAP.md` lists the steps by stable ID (`MS-n`), plus the settled and shelved decisions. Build only the steps Kiva has approved, ask before changing a settled decision, and tick the step when it merges. Finished steps go in the roadmap, not in this file.
- **One thread per feature:** finish it, test it and merge it before starting the next one.
- **Mock-ups first:** for any visible change, show a mock-up or screenshot and agree on the look before building it in full.
- **Checklist:** run through `.claude/CHECKLIST.md` before handing a round over.
- **Notes beside files:** every code file has a short note beside it (`name.md`: its purpose, then "Rules and pitfalls"). Read the note before editing the file. Add the rule or bug to the note when you fix one.
- **Merging:** Kiva asked (2026-11-27) that Claude merge its own PRs in this project once its checks pass (`build.py --check`, plus the snapshot comparison, `verify.py` and `layout.py` when the page changes), instead of leaving merges to Kiva. After merging, republish the artifact if `index.html` changed.
- **Style:** indent style and British or American spelling don't matter. Don't copy and paste: the third copy of the same few lines becomes a helper.
- **Summaries:** say plainly what was verified and what was only simulated or never seen for real.

**Edit `src/`, not `index.html`.** `index.html` is generated by `python3 build.py` (standard library only). Rebuild after every change, and run `python3 build.py --check` before publishing.
The sources are split into small files (MS-12, each under about 10 KB), so a change can be made by reading only the file it touches and its note. Concatenated in order, they give the same `index.html` byte for byte.
- `src/index.template.html`: head, top bar and the three panels, with `/*@CSS@*/`, `/*@JS@*/` and `<!--@INCLUDE name@-->` placeholders.
- `src/html/`: `dialogs-eq.html` (the five equation popups and the Components popup), `dialog-method.html` (method and check table), `dialog-sources.html` (sources [1]–[14]).
- `src/style.css`: styles.
- `src/js/`, concatenated in this order inside one block scope, so the files share names freely:
  - `physics.js`: constants, CMFs and colour, presets and state, `gamma`, `sublines`.
  - `plots-spectrum.js`: axes, the spectrum editor and the interfered spectrum. Moving d redraws only what depends on it: the editor is skipped when its inputs are unchanged (`specKey`), and the interfered spectrum keeps its axes, grid and S(σ) (`outC`) and re-evaluates only T(σ;δ₀).
  - `plots-range.js`: shared pixel maths, the anti-aliased range plots and the interferogram (trace cached, so only the δ₀ marker moves).
  - `ring-model.js`: ring model, `prepSL`, `pixVal`/`avgQ`.
  - `ring-shaders.js`: renderer state `RB`, `packRing`, the GLSL and WGSL sources.
  - `ring-gpu.js`: the WebGPU and WebGL2 renderers.
  - `ring-backends.js`: CPU workers and backend selection.
  - `ring-bench.js`: the startup speed test that ranks the renderers (MS-18).
  - `ring-preview.js`: adaptive preview resolution and the frame-rate measurement.
  - `ring-render.js`: `renderRing` and the profile.
  - `verify.js`: check table, coherence, live equations.
  - `ui-table.js`: components table, auto ranges, presets.
  - `ui-ring.js`: tilt dot (with the snap glide), field-of-view rim.
  - `ui-mirror.js`: mirror rail, schematic, sweep, readback, the ? popup.
  - `ui-loop.js`: editable numbers, ring sizing, dialogs, the draw loop (must stay last).

## Standing requirements (from the project owner, keep these true)

- **Everything must be mathematically verifiable.**
  - No faked visuals. Every rendered quantity uses the exact formula.
  - Each quantity has a row in the verification table (Method and checks → Run checks). The row compares it against an independent computation: Simpson quadrature, or a brute-force 2-D pixel integral.
  - Any new feature that renders a number or an image needs a check row.
- **Every formula is sourced.** The Sources dialog has numbered entries [1]–[14], and citation links open it and highlight the entry.
- **All formulas use LaTeX (MathJax), even in titles.**
  - No equation may need sideways scrolling, in the Method dialog or in the equation popups.
  - Put variable definitions on separate lines when needed. The live equations put 2 terms per line when the window is at least 900 px wide, otherwise 1.
- **Every number shown next to a control can be clicked and typed into.** Use `editable()`.
- **Layout: the page is tuned for a 16:9 screen recording.**
  - It's a single screen with no page scroll at 1920×1080, 1366×657 and 1280×600.
  - Layout "C, hero ring": source spectrum plus the Michelson panel on the left, the ring plus its profile in the middle, the interferogram, interfered spectrum and coherence on the right.
- **Wavelength axes are in nm and run 800 → 400 nm, left to right** (red on the left).
- **Heights are true heights, never rescaled.**
  - A Gaussian's height `a` is its peak spectral density, so its power is `I = √π·a·w`.
  - A line's power is `I = √π·a·w₀`, where w₀ corresponds to FWHM 0.008 µm⁻¹ (the width at which a dragged Gaussian snaps back to a line).
- **Controls are dragged, not slid.**
  - The mirror rail sets d; scroll on it to rescale the range.
  - The white dot on the ring sets the tilt. Only the dot can be dragged. It snaps to 0, 0 near the centre, and at 0, 0 it appears on hover. The snap glides over 300 ms (MS-9): the tilt value itself moves, so each frame shows the true pattern. Reset tilt and double-click glide too; with reduced motion it jumps.
  - Dragging the ring's rim, or scrolling on the ring, sets the field of view.
  - The sweep's pass time (−range to +range, default 8 s) and the mirror speed it implies sit in the rail header (MS-14). Both can be typed into or scrolled; the pass time stays the same when the range changes.
  - The Michelson schematic stays as a visual of what is happening. M₂ slides with d; the fixed mirror M₁ shows the tilt (MS-7): αx turns it either way in the drawing's plane, and αy leans it, drawn as a shaded strip of its face (+αy) or back (−αy).
- **Equations, notes, method and sources open as centred modal popups.**
  - Exception: the Components list is a non-modal popup at the bottom left.

## Physics (where it lives in src/js)

- Spectrum: lines plus Gaussians, `S(σ) = Σ I_n δ(σ−σ_n) + Σ a_n e^{−(σ−σ_n)²/w_n²}`, with `w = FWHM/(2√ln2)`. See `shape`, `dens`, `P`.
- Interferogram and coherence: `I(δ) = ½ Σ I_n [1 + e^{−(πw_nδ)²} cos 2πσ_nδ]` (Wiener–Khinchin). See `gamma`, `coherence`.
  - Coherence length is given two ways: the HWHM of |γ| and Mandel's ∫|γ|² dδ.
- Interfered spectrum: `S·½[1 + cos 2πσδ₀]` with δ₀ = 2d. See `renderOut`.
- Ring model:
  - `tanθ = r·tanθmax`
  - `δ = 2d cosθ + 2(αx·x + αy·y)`, with mirror coordinate scale `L·tanθmax` and L = 28.4 mm. See `ringModel`.
- Pixel averaging:
  - Each pixel is averaged over a Gaussian footprint with sd 0.5 px (`PIXSD`; MS-17, it was 0.4). A fringe at the pixel pitch keeps e^{−2π²·0.25} = 0.7% of its contrast; at 0.4 px it kept 4.2%, which showed as moiré (ghost ring centres). A preview grid point uses the same footprint scaled to its block, sd 0.5·k device px.
  - The first-order average has a closed form. A second-order correction (`avgQ`) is used when the fringe curvature matters (a 3e-4 test), at rest and in previews, on every renderer (MS-17: CPU and worker previews used to skip it, and coarse previews got the ring centre wrong).
  - Untilted, at rest, on the CPU (MS-15): the pattern and the pixel grid share the square's 8 symmetries, so only one octant of pixels is evaluated (exactly as every other pixel) and copied to its mirror pixels. The result is identical to evaluating every pixel. A moving untilted CPU preview still uses a radial grid (4 samples per grid pixel, linear interpolation). The GPU renderers evaluate every pixel.
  - In `pixVal` (CPU and workers), the terms that depend only on a sub-band's width are computed once per Gaussian (`avgQpre`), which is bit-identical.
  - First-order fast path: in an evenly spaced group (`g.lin`, set in `prepSL`), e^{ex} and the fringe cos/sin are stepped by exact ratios and re-evaluated directly every 16 sub-bands. It agrees with direct evaluation to < 1e-15 absolute (`tests/fastpath.js`). The −40 cut-off is exact: ex is monotonic along a group, so testing its two ends decides it for every sub-band, otherwise it is tested per sub-band (MS-16, bit-identical).
- Colour: each Gaussian is split into K sub-band Gaussians.
  - K is between 15 and 241, spanning ±2.8w, with each sub-band at most 0.012 µm⁻¹ wide. See `sublines`.
  - Each sub-band's XYZ is integrated over its own shape using the CVRL CIE 2006 2° CMFs (390–780 nm, embedded). Light outside that range adds no colour but still counts in the power.
  - XYZ is converted to sRGB, desaturated, gained per pattern and gamma-encoded.

## Renderers (ring image)

`RB` selects the renderer among WebGPU (compute and render, WGSL), WebGL2 (two passes into an RGBA32F target, GLSL), CPU workers (Blob workers running `pixVal`/`avgQ` source) and the CPU main thread. The page has no renderer control (MS-8). It starts on the first that works in that order; then a startup speed test (MS-18, `ring-bench.js`) has every available renderer compute the same fixed image (LED preset, 160² grid, warm-up plus median of 3, GPUs compute-only so the visible canvas is untouched) and switches to the fastest, ahead of the default order only when at least 10% faster. The ranking (`RB.rank`) is cached in localStorage per device (user agent, cores, GPU names, available renderers) for 30 days, so later visits start on the fastest; a failing renderer falls back to the next in the ranking. The test runs only at rest, after the first image is finished, and stops if anything moves. On this cloud host (no GPU), SwiftShader WebGL2 took 44 ms, workers 24 ms and one CPU core 48 ms, so it now picks the workers where it used to pick WebGL2. A round ? in the corner of the pattern panel opens a small popup with the renderer in use and the live resolution. The tests force one with the `?renderer=webgpu|webgl2|workers|cpu` address parameter (`use_renderer` in `tests/_common.py`), which also skips the speed test; the page lists what it found in `<html data-renderers data-renderer>` and the test's times in `data-bench`.

- **GPU precision:**
  - `k_b·2d mod 2π` is computed in float64 on the CPU (`packRing`). The GPU only adds `k_b·Δ`, where `Δ = −4d·sin²(θ/2) + kx·u + ky·v`.
  - sin and cos of θ come from square roots, not GPU trig.
  - The fringe cosine is `cosA`: range-reduced, then a Taylor series. GPU `cos` is only good to about 5e-4.
  - Do not "simplify" any of this back to built-ins. The tolerance is 1e-3, and builtin GPU trig failed it at d = 5 mm.
  - GPU fast path (MS-16): in a first-order, evenly spaced group, e^{ex} and the fringe cos/sin are stepped (as on the CPU) and re-evaluated with `exp`/`cosA` every 8 sub-bands (`GSTEP`). The phase step's large part, Δk_b·2d mod 2π, is also float64 from the CPU. Sub-band weights are premultiplied (P·X, P·Y, P·Z, P), so each sub-band is one fetch. A group whose first sub-band already has ex < −40 adds only its constant part. `tests/gpukernel.js` checks both kernels against `pixVal` (largest error 9e-6 of I, as before).
- **Verification:** the "Ring pixels" check reads back the **active** renderer's pixels (`ringReadback`) and compares them with brute-force integration.
- **Adaptive preview resolution while moving** (`LQ`, `lqPick`, `lqRecord`, `lqMotion`, `lqBudget`; MS-10, MS-11):
  - A preview is an Nl×Nl grid of exact footprint averages, Nl any whole number from N/16 to N, each over a block of k = N/Nl device pixels, scaled up (bilinear in XYZ/I on the GPUs, smooth canvas scaling on the CPU).
  - Resolution is continuous and driven by the last frame's measured time: cost t ≈ a·(N/k)^p (p = 1 radial, 2 otherwise), a updated after every preview frame, and the next k is the one predicted to take 90% of the budget, i.e. k·(t/0.9B)^(1/p). It goes coarser at once and finer half the way (log space) per frame.
  - The budget follows how fast the picture moves (Kiva: keep the *apparent* refresh rate, at the highest resolution). The fringe speed v (device px/ms) is the largest |Δδ|/|∇δ| between preview frames at 32 points; a frame may take as long as the motion needs to cross one preview pixel, T = k/v (capped at 100 ms, or 50 ms on the main-thread CPU), so B = base + max(0, T − FR). Slow drags get sharp previews; fast ones keep the display rate. A spectrum change or no recent frame counts as fast.
  - The sweep is a live input like a drag: each step calls `update(true)`, so the same fringe-speed budget sets its preview resolution, and stopping it renders the exact image (`tests/sweepres.js`).
  - When the inputs stop changing for 150 ms (`IDLE`) with the button still held, the exact at-rest image is rendered (`goIdle` in `ui-loop.js`).
  - Measurements expire after 3 s and reset when the number of sub-bands changes.
  - The budget follows the device: the display's refresh interval is measured from idle `requestAnimationFrame` steps (`measureFrame`, `FR()`, 25th percentile, clamped to 16.7–33.4 ms) and re-measured on resize and when the page becomes visible. CPU paths get what is left of that frame after the plots; GPU paths get 85% of it.
  - The profile and interferogram range plots do **not** adapt: always 8 sub-columns per pixel (`DPK`), moving or at rest (MS-17). MS-10 had them switch between 2 and 8 with the spare frame time, and dense fringes look very different at 2 and 8, so the plots flickered while dragging. `tests/plotstable.js` requires their pixels to be identical moving and at rest.
  - At rest, the image is always rendered at every pixel (Nl = N, the same code path and bit-identical outputs as before MS-11). On the CPU this is time-sliced into 12 ms slices so the page never blocks.
- **Hidden corners are skipped** (MS-13): the canvas is square but shown as a circle, so grid points with r > 1 + 3 grid cells (`rcut`) are stored as 0 instead of evaluated, on every renderer. Visible pixels are bit-identical; only the corner values in the snapshots change. Check points must stay inside the circle.
- Layout reads are cached (`box()`, `css()`, cleared on resize and theme change), and the interfered spectrum updates its existing SVG instead of rebuilding it (MS-13).
- Only one GPU or worker frame is in flight at a time (busy/dirty).
- The ring re-renders only when its inputs change (`ringInputs`, `renderRingIfNeeded`).

## Testing

```
pip install -r tests/requirements.txt && python -m playwright install chromium
python tests/verify.py          # runs the in-page verification table on every available renderer and preset
python tests/layout.py          # no page scroll / no equation overflow at 1920×1080, 1366×657, 1280×600
python tests/perf.py            # frame times and adaptive preview resolution while sweeping
python tests/autopick.py        # startup speed test: picks the fastest renderer, caches it, checks pass on it (MS-18)
```

Before and after any refactor or optimization, check that the physics is unchanged (Node, `npm i playwright`):

```
node tests/snapshot.js index.html before.json     # on the old build
node tests/snapshot.js index.html after.json      # on the new build
python3 tests/compare_snapshots.py before.json after.json   # IDENTICAL, or the largest difference per output
node tests/fastpath.js                            # pixVal's stepped fast path vs direct evaluation
node tests/symmetry.js                            # untilted at-rest ring: octant mirrored 8 ways vs every pixel evaluated (MS-15)
node tests/gpukernel.js                           # WGSL and GLSL pixel kernels alone vs pixVal in float64 (MS-16)
node tests/antialias.js                           # previews at several grid sizes vs brute-force footprint integrals, and moiré on a dense ring, every renderer (MS-17)
node tests/plotstable.js                          # profile and interferogram pixels identical moving and at rest (MS-17)
node tests/sweepres.js                            # the sweep drives the adaptive preview like a drag: live frames, measured fringe speed, finer when slower, exact when stopped
```

`snapshot.js` records every output for 7 spectra on the CPU, worker and WebGL2 renderers. Two runs of the same build are identical, so any difference is real. Only accept a difference at floating-point noise level, and say so. Since MS-13, `ring` and `Ib` differ from pre-MS-13 builds in the hidden corners (r > rcut) only. Since MS-17 (footprint sd 0.4 → 0.5 px), `ring`, `Ib`, `ifgC` (the interferogram colours) and the check table differ from pre-MS-17 builds on purpose; everything else (γ, sub-bands, coherence, plot SVGs, `profC`, equations, readouts) must stay identical.

- Offline, or with the CDN blocked: `npm i mathjax@3.2.2`, then set `MATHJAX_DIR=…/node_modules/mathjax` and the tests serve MathJax from there.
- `GPU_ARGS=0` launches Chromium without the WebGPU/Vulkan flags. On hosts without a GPU those flags can make both GPU contexts get lost; the page then falls back to the CPU. With `GPU_ARGS=0`, WebGL2 still runs on SwiftShader, and `tests/gpukernel.js` checks the WebGPU kernel on its own.
- Use a Playwright version that matches the installed Chromium.

Headless Chrome can't display WebGPU canvases, so screenshots there show WebGPU as black. Its numbers are still checked through readback. Use `--use-angle=swiftshader` for WebGL2 without a GPU.

## Known gaps (never seen for real)

These were only checked in headless Chromium on a cloud machine without a GPU. Kiva, please confirm them on a real machine.

- The WebGPU ring has only been checked through its readback numbers (since MS-16, on this host, through `tests/gpukernel.js`'s compute-only run on SwiftShader, because the full page loses its GPU contexts here).
- The MS-16 GPU speed-up (about 2× per sub-band) was measured on SwiftShader only. On a real GPU, where exp and cos are cheaper relative to memory reads, the gain may be smaller. Headless Chrome shows WebGPU canvases as black, so nobody has looked at its image in a test.
- WebGL2 was tested through SwiftShader (software rendering), not on a real GPU.
- The sweep time (MS-14) was checked by the Sweep row and by timing scripted sweeps in headless Chromium (about 40 µm/s measured for a set 40 µm/s); how a very short or very long pass looks on a real screen has not been seen.
- Frame times and the adaptive preview resolution (`tests/perf.py`) were measured on the cloud machine, not on Kiva's hardware. That includes the device scaling (MS-10): the refresh-rate measurement only ever saw a 60 Hz headless display, and 30 Hz was simulated by forcing `FR()`. The motion-driven budget (MS-11) was checked only with scripted rail drags at fixed speeds in headless Chromium (SwiftShader WebGL2, workers, CPU); how smooth slow drags look on a real screen has not been seen.
- The startup speed test (MS-18) has only run here, comparing SwiftShader WebGL2 with the CPU workers and the main thread. It has never timed WebGPU (the full page loses its WebGPU context on this host) or a real GPU, so whether it picks the GPU on Kiva's machine, and the times it shows in the ? popup there, have not been seen.
- The layout checks ran in headless Chromium only. Firefox and Safari have never been tested.
- MS-17 (plot flicker, moiré) was reproduced and checked in headless Chromium on CPU, workers and SwiftShader WebGL2, by pixel comparisons and brute-force integrals. Kiva saw both problems on a real machine; whether the fix looks right there has not been seen. The WebGPU preview path was checked only through `tests/gpukernel.js` here, since the full page loses its WebGPU context on this host.
